# Changelogs de Liquibase — AccesMed

Aplicá esta convención cada vez que toques el esquema de base de datos. La idea de fondo:
**un archivo por entidad, que acumula toda su historia** — no un archivo por cambio. Esto
mantiene el `db.changelog-master.yaml` casi sin tocar con el tiempo, a costa de un
trade-off menor de control de versiones (ver el final).

## 1. Decidir: ¿archivo nuevo o changeset agregado?

- **La entidad no tiene changelog todavía** (primera vez que se persiste): creá un archivo
  nuevo con el changeset `created`, e incluilo **una vez** en el master.
- **La entidad ya tiene changelog**: **nunca crees un archivo nuevo ni modifiques un
  changeset ya ejecutado**. Agregá un changeset nuevo al final del archivo existente. El
  master no se toca — ya la incluye desde que se creó.

Si no sabés si la entidad ya tiene changelog, buscá en `src/main/resources/db/changelog/changes/`
un archivo que termine en `-<NombreEntidad>.yaml`.

## 2. Nombre del archivo

```
YYYYMMDDHHMMSS-<NombreEntidad>.yaml
```

El timestamp es la **fecha de creación del archivo** (cuando se agregó el primer
changeset) y **no cambia** aunque el archivo acumule changesets nuevos después — el
nombre no describe "la última vez que se tocó", describe "cuándo empezó a existir esta
tabla". Ejemplo: `20260301120000-Prestacion.yaml`.

`<NombreEntidad>` es el nombre de la entidad JPA tal cual (PascalCase), no el nombre de la
tabla en snake_case (`Prestacion`, no `prestacion`).

## 3. Id de cada changeset

```
YYYYMMDDHHMMSS-<acción>
```

El timestamp acá es propio de **ese** changeset (la fecha en que se agregó), no la del
archivo — salvo el primero, que coincide con el nombre del archivo. Vocabulario fijo de
acciones (no inventes otras sin que el usuario lo pida):

| Acción | Cuándo usarla |
|---|---|
| `created` | Primer changeset del archivo: crea la tabla. Misma fecha que el nombre del archivo. |
| `added-column-<nombre>` | Agrega una columna. |
| `dropped-column-<nombre>` | Elimina una columna. |
| `modified-column-<nombre>` | Cambia tipo, nullabilidad o default de una columna existente. |
| `added-constraint-<nombre>` | Agrega una constraint (UNIQUE, CHECK, FK) que no vino con `created`. |
| `added-index-<nombre>` | Agrega un índice. |
| `renamed-column-<nombre>-to-<nuevoNombre>` | Renombra una columna. |
| `dropped-table` | Elimina la tabla completa. Muy poco común: el proyecto usa soft delete, así que un DROP TABLE real casi nunca es lo que se quiere — confirmá con el usuario antes de usar esta acción. |

`author` en cada changeset: el nombre de usuario de quien lo agrega (por defecto usá el
que ya aparece en changesets anteriores del mismo archivo, para no mezclar autores sin
motivo).

## 4. Mapeo de tipos: Java/JPA → columna de Postgres

Usá esta tabla para traducir cada campo de la entidad a su columna Liquibase. Cuando el
campo tenga anotaciones de Bean Validation o JPA que acoten el tipo (`@Size`, `@Column`),
esas anotaciones mandan por sobre el default de la tabla.

| Tipo Java | Tipo de columna (Liquibase) | Notas |
|---|---|---|
| `Long` (PK con `@GeneratedValue`) | `BIGINT`, `autoIncrement: true` | Postgres: `GENERATED BY DEFAULT AS IDENTITY` vía Liquibase. |
| `Long` (FK u otro numérico) | `BIGINT` | |
| `Integer` / `int` | `INT` | |
| `String` | `VARCHAR(255)` | Si hay `@Size(max = N)` o `@Column(length = N)`, usar `VARCHAR(N)`. Texto largo sin límite: `TEXT`. |
| `Boolean` / `boolean` | `BOOLEAN` | |
| `BigDecimal` | `DECIMAL(19,2)` | Ajustar precisión/escala si `@Digits` o el dominio lo pide (ej. montos vs. porcentajes). |
| `LocalDate` | `DATE` | |
| `LocalDateTime` | `TIMESTAMP` | Estándar para columnas de auditoría y horarios con fecha+hora. |
| `LocalTime` | `TIME` | |
| `Enum` de Java | `VARCHAR(50)` | Se persiste el nombre del enum como texto (`@Enumerated(EnumType.STRING)` del lado JPA), nunca el ordinal. |
| `UUID` | `UUID` | Postgres tiene tipo nativo. |
| `byte[]` | `BYTEA` | |

## 5. Columnas de auditoría y soft delete (`Auditable`)

Toda entidad que extiende `Auditable` trae estas columnas en su `created`:

```yaml
- column: { name: fecha_hora_alta, type: TIMESTAMP, constraints: { nullable: false } }
- column: { name: fecha_hora_modificacion, type: TIMESTAMP }
- column: { name: usuario_alta, type: VARCHAR(255), constraints: { nullable: false } }
- column: { name: usuario_modificacion, type: VARCHAR(255) }
```

**El soft delete no es automático para toda entidad.** Antes de agregar `fecha_hora_baja`
(o `fecha_hora_fin_vigencia`, según la entidad — ver `CLAUDE.md`), **preguntá si esta
entidad en particular usa baja lógica** si no es obvio por el diagrama de clases o por lo
que ya te dijo el usuario. No asumas que todas las entidades la tienen: es una duda
abierta del proyecto (ver `ARQUITECTURA.md`), así que ante la duda, preguntar es mejor que
generalizar de más.

```yaml
- column: { name: fecha_hora_baja, type: TIMESTAMP }   # solo si la entidad tiene soft delete
```

## 6. Relaciones (FK)

Para una relación `N→1` (ej. `Turno → AgendaMedicoHorariosRango`), agregá la columna FK
dentro del mismo `createTable` y la constraint junto con ella (o en un changeset
`added-constraint-<nombre>` aparte si se agrega después de que la tabla ya existe):

```yaml
- column: { name: agenda_medico_horarios_rango_id, type: BIGINT, constraints: { nullable: false } }
```

```yaml
- changeSet:
    id: 20260301120500-added-constraint-fk-turno-agenda-rango
    author: fsorrentino
    changes:
      - addForeignKeyConstraint:
          baseTableName: turno
          baseColumnNames: agenda_medico_horarios_rango_id
          referencedTableName: agenda_medico_horarios_rango
          referencedColumnNames: id
          constraintName: fk_turno_agenda_medico_horarios_rango
```

Respetá la navegabilidad del diagrama de clases: si el proyecto dice que a `Medico`/
`Prestacion` desde `Turno` se llega **solo vía `MedicoPrestacion`**, no agregues una FK
directa de `Turno` a `Medico` aunque técnicamente se podría — el modelo de datos sigue al
diagrama, no al atajo que sería más fácil de escribir.

## 7. Master changelog

`src/main/resources/db/changelog/db.changelog-master.yaml` recibe **un `include` por
archivo, solo cuando el archivo se crea** (primer changeset, `created`). Los changesets
que se agreguen después al mismo archivo **no** requieren tocar el master — ya está
incluido.

```yaml
databaseChangeLog:
  - include:
      file: db/changelog/changes/20260301120000-Prestacion.yaml
```

## 8. Ejemplo completo: archivo con varios changesets acumulados

```yaml
databaseChangeLog:
  - changeSet:
      id: 20260301120000-created
      author: fsorrentino
      changes:
        - createTable:
            tableName: prestacion
            columns:
              - column: { name: id, type: BIGINT, autoIncrement: true, constraints: { primaryKey: true } }
              - column: { name: codigo, type: VARCHAR(50), constraints: { nullable: false, unique: true } }
              - column: { name: nombre, type: VARCHAR(255), constraints: { nullable: false } }
              - column: { name: duracion_turno_minutos, type: INT, constraints: { nullable: false } }
              - column: { name: fecha_hora_alta, type: TIMESTAMP, constraints: { nullable: false } }
              - column: { name: fecha_hora_modificacion, type: TIMESTAMP }
              - column: { name: usuario_alta, type: VARCHAR(255), constraints: { nullable: false } }
              - column: { name: usuario_modificacion, type: VARCHAR(255) }
              - column: { name: fecha_hora_baja, type: TIMESTAMP }
  - changeSet:
      id: 20260315091500-added-column-tiempoToleranciaAnuncio
      author: fsorrentino
      changes:
        - addColumn:
            tableName: prestacion
            columns:
              - column: { name: tiempo_tolerancia_anuncio, type: INT }
```

## 9. Trade-off a tener presente

Un archivo por entidad significa que si dos ramas modifican la misma entidad al mismo
tiempo, van a chocar en el mismo archivo al mergear — más probable que con un archivo por
cambio. Para el tamaño de este equipo es manejable: alcanza con coordinar quién toca qué
entidad en un momento dado. No es motivo para volver al esquema de un archivo por cambio.

## Checklist

- [ ] Archivo nuevo solo si la entidad no tenía changelog; si ya existía, se agregó un
      changeset al archivo existente (nunca se creó uno paralelo ni se tocó uno viejo).
- [ ] Nombre de archivo `YYYYMMDDHHMMSS-<NombreEntidad>.yaml` con el timestamp de creación,
      sin actualizar aunque se agreguen changesets nuevos.
- [ ] Id del changeset con el vocabulario fijo (`created`, `added-column-...`,
      `dropped-column-...`, `modified-column-...`, `added-constraint-...`,
      `added-index-...`, `renamed-column-...-to-...`, `dropped-table` solo confirmado).
- [ ] Tipos de columna según la tabla de mapeo Java → Postgres; `@Size`/`@Column(length)`
      respetados si están.
- [ ] Columnas de `Auditable` presentes; `fecha_hora_baja` (o `fecha_hora_fin_vigencia`)
      **solo si se confirmó** que la entidad tiene soft delete — si hay duda, se preguntó.
- [ ] FKs siguiendo la navegabilidad real del diagrama de clases, no un atajo.
- [ ] Master changelog: un `include` por archivo, agregado solo cuando el archivo se creó.
